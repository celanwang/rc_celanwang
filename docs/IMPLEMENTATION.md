# API 通知系统实施与验收

## 交付目标

建设一个持久化接收、异步投递和故障后可恢复的通知服务。业务方提交已构造的 HTTP(S) 请求，服务以有效 `2xx` 响应确认投递；允许重复请求，不保证供应商业务效果恰好一次。

任务由 `notification` 保存，尝试历史由 `notification_attempt` 保存。接收提交后返回任务 ID，后台根据等待、处理中、成功、失败四种状态执行；暂时故障受控重试，自动处理停止后保留原因和重放入口。

本轮交付是文档整理。服务代码、运行环境和运行验收尚未完成；以下条件用于后续实施，不是测试通过记录。

## 建设顺序

实现按可检查的纵向流程推进。每一步交付可运行或可验证的结果，再扩展后续能力，避免先铺设大量没有执行路径的抽象。

| 阶段 | 输出 | 进入下一阶段的条件 |
|---|---|---|
| 工程基础 | Go module、配置校验、MySQL migration、API 类型和状态枚举 | 固定工具链可构建，迁移可重复执行，配置错误可定位 |
| 接收与单次投递 | 接收幂等、持久化、HTTP 外呼、任务查询 | 正常请求、同键重试、内容冲突和数据库失败用例通过 |
| 调度与恢复 | 退避、租约、条件写回、尝试历史 | 并发领取、进程崩溃、迟到写回和恢复用例通过 |
| 运行管理 | 目标隔离、地址与传输限制、重放、指标和数据清理 | 长期故障可发现、可定位、可恢复，权限与资源限制有效 |
| 提交验收 | 可复现运行说明、演示脚本、测试结果、AI 协作记录 | 必验场景有证据，运行命令实际可执行，限制明确 |

建设中只修订实际受影响的契约和文档。README 保持问题理解、架构与取舍的职责，运行步骤与验证结果由建设材料记录。

## 验证方式

验收按 MVP 控制投入：证明主要功能可用、持久化与恢复规则成立，并覆盖直接影响投递结果的少量边界。减少验收规模不改变成功判定、鉴权、幂等、租约和重试等功能要求，也不将已发现的问题留作“以后再测”。

Go 单元测试优先覆盖状态转移、错误分类与重试预算，使用少量表驱动用例；时钟和随机源可控，不真实等待完整重试周期。简单数据结构、访问器和只重复实现逻辑的测试不单独铺开，不设覆盖率或测试数量目标。

HTTP 使用 `httptest` 或一个轻量模拟供应商，复用它完成成功、错误和超时验证。数据库集成使用真实 MySQL，重点检查唯一约束、任务领取和条件写回，SQLite 或存储 Mock 不能替代。用一次本地服务重启演示恢复，剩余租约边界通过可控状态验证，不为每个故障点建设进程注入平台。

功能合并验证，避免同一行为在多层重复测试。运行格式检查、构建、静态检查和核心测试，再完成一次本地集成演示；通过后进入交付，仅在代码变化、失败或具体风险出现时追加与重跑相应检查。

## 必验场景

以下五组是 MVP 的完成门槛。每组用少量代表性用例验证，不要求遍历所有状态码、错误组合或运行环境。

| 场景 | 可观察的通过条件 |
|---|---|
| 主流程 | HTTP/HTTPS 的 Method、Header、Body 正确，提交后可查询任务与尝试；`200` 正文业务失败和 `202` 均按投递成功处理；失败任务可受控重放并保留历史 |
| 接收一致性 | 并发同键同内容只建一条任务，不同内容返回 `409`；数据库不可用时不虚假确认接收 |
| 失败处理 | 用 `400`、`429`、`503` 和超时验证停止或重试；覆盖 Retry-After 的必要解析及次数、有效期边界；没有 Go error 也按状态判定 |
| 恢复与执行权 | 一次重启演示已接收任务不丢失；真实 MySQL 验证竞争领取、过期租约回收与旧令牌写回被拒绝 |
| 基本防护 | 代表性用例确认未授权访问与非法目标被拒绝、TLS 正常验证、重定向不自动跟随；请求超时与大小限制生效，日志不暴露凭证 |

状态、重试和执行权用例应能发现规则错误，不依赖只返回预设成功结果的 Mock。模拟供应商的观察只能证明测试环境中的行为，不能描述为真实供应商已经验证。

## 按需检查

以下检查不作为第一版默认完成条件，只有实现暴露具体风险或后续需求明确时再开展：

- 数据库提交结果不明、死锁和网络分区的系统性故障注入。
- 供应商已执行但本地未确认的全链路故障组合、所有租约竞争时序。
- 全部 HTTP 状态、证书失败类型、DNS 绕过方式与协议组合的穷举。
- 长时间运行、容量压测、跨平台矩阵、多副本高可用、灾难恢复和外部告警平台联调。

数据清理等可能影响持久记录的实现若出现新的风险，应增加针对性的检查。无需为了完成 MVP 建设专用测试平台、引入复杂 Mock 框架或反复运行无新增信息的全量回归。

## 实验参数

以下数值作为开发与测试起点，不是 PRD 指定参数或性能承诺。实现配置应能调整，并在每次运行证据中记录实际值。

| 参数 | 起点 |
|---|---|
| 总超时 / 连接 / TLS / 响应头 | 10 秒 / 3 秒 / 3 秒 / 5 秒 |
| 租约 / 扫描间隔 | 30 秒 / 1 秒 |
| 全局 / 单目标并发 | 20 / 4；领取量不超过当前空闲容量 |
| 本轮最多尝试 / 有效期 | 20 次，包含首次 / 24 小时，先耗尽者生效 |
| 重试基础 / 最大间隔 / 最小等待 | 5 秒 / 1 小时 / 1 秒 |
| 正文 / 外呼请求头 / 响应头 / 诊断正文上限 | 1 MiB / 16 KiB / 32 KiB / 16 KiB；外层提交另设总上限 |
| 终态保留 | 终态后 30 天，活动任务不清理 |

阶段超时受总超时约束，租约需要覆盖单次执行和写回余量。次数可能早于有效期耗尽，不能把配置 24 小时描述为持续重试满 24 小时。领取后的崩溃也可能消耗一次尝试预算，测试应区分执行尝试与实际网络发送。

后续确需容量测试时，固定机器资源、MySQL 版本、请求大小、供应商延迟、到达率和目标配额，再记录积压、延迟和资源。第一版不以容量压测作为交付门槛，也不据实验参数承诺性能。

## 验收证据

在一份简短记录中保存必要的环境、命令、核心场景结果和限制即可，无需为每个用例另建报告。恢复场景保留前后任务与尝试状态，必要时补充模拟供应商记录，数据均需脱敏。

检查通过只支持实际覆盖的行为。格式检查不等于运行验收，单机恢复不等于数据库灾难恢复，单进程并发限制不等于多副本全局配额。告警渠道需要在实际部署中验证，只有日志或指标不能记录为已接入告警。

五组必验场景、构建与基础检查通过，运行说明可复现，且没有未解决的核心功能缺陷后，即可完成 MVP 交付。按需检查未执行不阻止交付，应如实说明覆盖范围；必验项目未通过或因环境未执行时，不能标记为全部完成。达到完成条件后停止扩展测试和非必要重构。
