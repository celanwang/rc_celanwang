# AI 使用说明

## 协作起点

这次作业从需求讨论开始。开发者先要求 AI 阅读需求、拆解问题，暂缓代码实现。可靠通知看起来只是发送 HTTP 请求，但接收成功意味着什么、超时后是否重试、进程退出后如何恢复，都需要先说清楚。这些约定会直接影响后面的代码。

AI 主要参与方案比较、故障场景分析、资料核对和文档整理。开发者负责补充约束、检查建议是否符合题意，并决定哪些内容进入第一版。讨论按具体问题逐步推进，已经确定的要求继续沿用，有疑问的地方再展开。

## 几次关键调整

最早的方案建议使用 PostgreSQL。开发者随后明确采用 Go 和 MySQL，工具链与本机 Go 1.26.0 对齐，module 使用 `github.com/celanwang/rc_celanwang`。数据库选择改变后，AI 重新核对 MySQL 的任务领取、事务隔离和条件更新，相关设计也随之调整。

HTTP/HTTPS 模块是另一处被要求继续细化的内容。最初的整体架构还不足以说明各种错误应该怎样处理，开发者要求把传输过程和错误码单独展开。后续才明确区分了接入接口的错误、供应商返回的状态，以及没有取得响应时的网络异常。

成功判定由开发者明确限定：第一版仅根据 HTTP 状态确认投递。AI 讨论过的正文业务码解析和后续结果查询因此没有进入方案。这个选择保留了统一的投递规则，也意味着收到 `200` 时无法识别正文里的业务失败，收到 `202` 后不会继续等待供应商处理完成。范围收窄后，相应限制也需要写清楚。

生命周期的表达也经过调整。开发者提出引入状态机，并要求两张表的命名更简洁。AI 据此细化为四种任务状态，分别保存通知与投递尝试。状态名称、字段和 SQL 细节由 AI 整理，开发者提出的重点是让任务处于什么阶段、为什么转移、失败后怎样恢复都能被看懂。

文档也有过返工。README 一度写成项目简介和文档导航，开发者将它重新限定为问题理解、整体架构和工程取舍三个主题。之后又提供另一项目的任务与文档作为参考，调整标题、段落和内容分工，减少重复。这些反馈给出了具体修改方向，避免只要求 AI 泛泛地“继续优化”。

## 复杂度取舍

消息队列是讨论中的一个典型选择。异步通知经常使用队列，但本项目已经有 MySQL，可以先用持久化任务、调度时间和 Worker 完成投递。增加独立队列，还要处理消息发布、消费确认，以及队列和数据库状态不一致的情况。

开发者据此选择让第一版先保持单服务和 MySQL 任务调度。没有实际流量瓶颈或独立消费需求时，额外组件带来的收益还不明确，部署、测试和排障却会多出一层责任。这个选择也有代价：轮询和频繁更新会占用数据库资源，后续需要通过容量测试判断是否继续适用。

框架和模块采用同样的取舍方式。Go 标准库、显式 SQL 和少量接口可以承载当前职责，通用工作流、供应商适配平台和多服务拆分暂不建设。AI 曾讨论的 `needs_review` 人工核查流程，也在方案细化中收敛为不确定结果记录与受控重放，没有继续扩展出一套独立流程。

这些调整减少了需要维护的组件和通用能力，接收幂等、持久化、租约恢复、条件写回和失败历史仍然保留。判断一项设计是否过度，要看它是否解决了当前问题，以及去掉后会失去什么。涉及可靠性的必要机制，即使实现起来麻烦，也需要有明确安排。

## 核对与验证

AI 提供的技术解释需要核对。本轮通过 AI 工具读取了本机 Go 文档，并查阅 MySQL 官方文档、HTTP 语义规范和 SSRF 防护资料。其中一个具体发现是：Go HTTP Client 收到 `4xx` 或 `5xx` 时通常不会返回 Go error；Transport 在特定条件下还可能自动重试。因此，结果分类不能只看 `err`，一次函数调用也不能简单记作一次实际网络发送。

故障分析还暴露了一个重要边界：供应商可能已经执行请求，但通知服务没有收到响应。重新发送有助于避免漏送，也可能重复产生副作用。方案保留了这一不确定性，接收幂等与供应商幂等分别处理，没有把“可靠送达”写成“恰好一次”的保证。

语言、数据库和成功判定是开发者明确的约束；MySQL 具体版本基线、字段细节和实验参数则来自 AI 的建议。后者仍需要在实现中核对，尤其是超时、并发和重试次数，不能因为写进文档就视为已经验证。

进入实现后，AI 按工程基础、接收与投递、调度与恢复、运行管理和交付的顺序生成代码，并在每段完成后运行相应检查。开发者给出的契约继续作为判断标准，没有重新引入消息队列、Redis、工作流或管理后台。常规选择包括 `go-sql-driver/mysql` 1.10.1、MySQL 8.4.7 补丁版本、环境变量配置和标准库 HTTP 路由。

实现过程中，测试实际发现并修正了一个数据库扫描问题：可空的领取令牌最初直接扫描进字符串，在真实 MySQL 返回 `NULL` 时失败，随后改用 `sql.NullString`。接收软水位检查也经过复核，保证积压达到水位时，相同内容的幂等重试仍能返回已有任务。时间字段随后调整为读取或写入数据库 UTC，避免调度边界同时依赖两个时钟。

AI 还补充了私有 CA 文件支持，而没有采用跳过 TLS 校验的便捷做法；正向 HTTPS 用例把测试证书加入独立信任池，反向用例确认未知证书停止投递。日志和查询输出经过收敛，不保存 URL、正文、凭证或原始传输错误，只保留任务关联字段、安全错误码和有限诊断事实。

最终使用真实 MySQL、`httptest` 和本地模拟供应商完成检查。持久任务在服务停止前保持 `pending`，重启后变为 `succeeded`；竞争领取、过期租约接管和旧令牌写回拒绝由数据库集成用例验证。没有开展性能压测、数据库网络分区、灾难恢复或外部告警联调，因此没有把这些能力描述成已验证结果。

## 协作体会

这轮协作中，AI 帮助展开了故障场景，也把分散的讨论整理成了接口、状态和验收规则。开发者的参与则体现在几次具体调整里：确定技术约束，收窄成功判定，要求补清错误处理，控制组件数量，以及反复修正文档的职责和表达。

使用 AI 时，容易低估的是检查前提所需要的工作。一段方案即使解释得很顺，也可能依赖尚未确认的需求，或者把未来可能用到的能力放进第一版。持续追问适用条件、保留必要取舍，并把不确定的结论交给验证，才能让讨论真正帮助项目向前推进。

最终取舍和提交边界仍由开发者负责。本文如实保留 AI 提供的帮助、没有采用的建议、实现中修正的问题和未验证范围，使协作说明与最终代码及验收证据一致。
