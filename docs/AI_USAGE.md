# AI 使用说明

## 协作起点

这次作业从需求讨论开始。开发者先要求 AI 阅读需求、拆解问题，暂缓代码实现。可靠通知看起来只是发送 HTTP 请求，但接收成功意味着什么、超时后是否重试、进程退出后如何恢复，都需要先说清楚。这些约定会直接影响后面的代码。

AI 参与方案比较、故障场景分析和资料核对，在边界确定后继续完成代码生成、检查和文档整理。开发者负责补充约束、判断建议是否符合题意，并决定哪些内容进入第一版。讨论按具体问题逐步推进，已经确定的要求继续沿用，有疑问的地方再展开。

这次协作关注的是每项选择能否说清依据。先明确来自需求的约束，再说明候选方案的成本，最后用代码和运行结果检查判断，使建议、决定与证据能够对应起来。开发者保留取舍与交付标准的决定权，AI 的具体建议则允许被后续证据修正。

## 几次关键调整

最早的方案建议使用 PostgreSQL。开发者随后明确采用 Go 和 MySQL，工具链与本机 Go 1.26.0 对齐，module 使用 `github.com/celanwang/rc_celanwang`。数据库选择改变后，AI 重新核对 MySQL 的任务领取、事务隔离和条件更新，相关设计也随之调整。

HTTP/HTTPS 模块是另一处被要求继续细化的内容。最初的整体架构还不足以说明各种错误应该怎样处理，开发者要求把传输过程和错误码单独展开。后续才明确区分了接入接口的错误、供应商返回的状态，以及没有取得响应时的网络异常。

成功判定由开发者明确限定：第一版仅根据 HTTP 状态确认投递。AI 讨论过的正文业务码解析和后续结果查询因此没有进入方案。这个选择保留了统一的投递规则，也意味着收到 `200` 时无法识别正文里的业务失败，收到 `202` 后不会继续等待供应商处理完成。范围收窄后，相应限制也需要写清楚。

生命周期的表达也经过调整。开发者提出引入状态机，并要求两张表的命名更简洁。AI 据此细化为四种任务状态，分别保存通知与投递尝试。状态名称、字段和 SQL 细节由 AI 整理，开发者提出的重点是让任务处于什么阶段、为什么转移、失败后怎样恢复都能被看懂。

文档也有过返工。README 一度写成项目简介和文档导航，开发者将它重新限定为问题理解、整体架构和工程取舍三个主题。之后又提供另一项目的任务与文档作为参考，调整标题、段落和内容分工，减少重复。这些反馈给出了具体修改方向，避免只要求 AI 泛泛地“继续优化”。

进入代码阶段前，开发者要求把已确定的内容整理为 Goal 提示词，明确实现范围、必要验证、阶段提交与停止条件。常规工程细节交给 AI 处理，核心契约继续受约束。验收也被主动收窄为五组核心行为，避免实现结束后继续扩展测试平台或通用能力；出现具体问题时仍需补充相应检查。

## 复杂度取舍

消息队列是讨论中的一个典型候选。在已经确定使用 MySQL 的前提下，持久化任务、调度时间和 Worker 可以组成投递流程。增加独立队列，还要处理消息发布、消费确认，以及队列和数据库状态不一致的情况。这些责任不能因为组件成熟就忽略。

开发者据此选择让第一版先保持单服务和 MySQL 任务调度。没有实际流量瓶颈或独立消费需求时，额外组件带来的收益还不明确，部署、测试和排障却会多出一层责任。这个选择也有代价：轮询和频繁更新会占用数据库资源，后续需要通过容量测试判断是否继续适用。

框架和模块采用同样的取舍方式。Go 标准库、显式 SQL 和少量接口可以承载当前职责，通用工作流、供应商适配平台和多服务拆分暂不建设。AI 曾讨论的 `needs_review` 人工核查流程，也在方案细化中收敛为不确定结果记录与受控重放，没有继续扩展出一套独立流程。

建议的来源也需要如实记录。PostgreSQL 和正文业务码判定，是被开发者明确的技术选择与成功边界替换的建议；消息队列等能力是评估后没有纳入的候选，并非 AI 坚持引入、再由人工全部推翻。保留这些区别，才能说明真实的判断过程。

这些调整减少了需要维护的组件和通用能力，接收幂等、持久化、租约恢复、条件写回和失败历史仍然保留。判断一项设计是否过度，要看它是否解决了当前问题，以及去掉后会失去什么。涉及可靠性的必要机制，即使实现起来麻烦，也需要有明确安排。

## 核对与验证

AI 提供的技术解释需要核对。本轮通过 AI 工具读取了本机 Go 文档，并查阅 MySQL 官方文档、HTTP 语义规范和 SSRF 防护资料。其中一个具体发现是：Go HTTP Client 收到 `4xx` 或 `5xx` 时通常不会返回 Go error；Transport 在特定条件下还可能自动重试。因此，结果分类不能只看 `err`，一次函数调用也不能简单记作一次实际网络发送。

故障分析还暴露了一个重要边界：供应商可能已经执行请求，但通知服务没有收到响应。重新发送有助于避免漏送，也可能重复产生副作用。方案保留了这一不确定性，接收幂等与供应商幂等分别处理，没有把“可靠送达”写成“恰好一次”的保证。

语言、数据库和成功判定是开发者明确的约束；MySQL 具体补丁版本、字段细节和实验参数则来自 AI 的实现选择。选定版本可以通过环境核对，超时、并发和重试次数是否适合实际负载仍需运行依据，不能因为写进文档就视为已经验证。

进入实现后，AI 按工程基础、接收与投递、调度与恢复、运行管理和交付的顺序生成代码，并运行相应检查，形成四次阶段提交。提交沿用仓库的类型、范围和中文简述格式，代码与相关测试按逻辑归组，便于回看每次变更的内容。常规选择包括 `go-sql-driver/mysql` 1.10.1、MySQL 8.4.7、环境变量配置和标准库 HTTP 路由，没有增加消息队列、Redis、工作流或管理后台。

实现过程中，测试发现可空的领取令牌最初直接扫描进字符串，在真实 MySQL 返回 `NULL` 时失败，随后改用 `sql.NullString`。接收软水位逻辑也增加了查询已有任务的分支，使积压限制不直接挡住同内容的幂等重试。任务创建、领取等调度操作采用数据库 UTC 时间；其他时间相关路径仍需分别核对，不能据此概括为整个实现已经完全消除时钟差异。

AI 还补充了私有 CA 文件支持；正向 HTTPS 用例把测试证书加入信任池，反向用例确认未知证书停止投递。普通日志与任务查询响应不输出请求 URL、正文和凭证，尝试摘要只保留安全错误码与有限诊断事实。数据库仍保存投递所需的原始请求，输出脱敏不等于请求内容未被存储。

实现任务记录了真实 MySQL、`httptest` 和本地模拟供应商下的检查。重启演示中，持久任务在服务停止前保持 `pending`，重启后变为 `succeeded`；竞争领取、过期租约接管和旧令牌写回拒绝有相应数据库集成用例。没有开展性能压测、数据库网络分区、灾难恢复或外部告警联调。这些结果支持已经检查的路径，不代表所有实现细节都正确。

## 交付复核

实现任务报告完成后，开发者又要求按此前约定评估实际代码。复核重新读取任务记录、提交和源码，运行少量基础测试，并在临时副本中构造具体反例，检查完成报告之外的行为。

这一轮发现了三类问题。不同 Header 结构可能得到相同请求摘要，同一份含大小写重复 Header 的输入也可能得到不同摘要；这两种情况已在临时副本复现。调度代码还可能让已删除目标的旧任务占住候选结果，使有效目标得不到执行机会。集成测试则存在无条件清表，运行说明使用的测试数据库没有与服务示例数据隔离。

已有基础测试在复核时仍然通过，说明问题在原有覆盖范围之外。复核没有继续运行会清表的数据库测试，也没有把发现问题写成已经修复。这三类问题仍需修正并补充定向回归；此前的完成报告不能作为它们已经解决的依据。

这也是验收范围需要保留判断空间的原因。MVP 可以不做穷举和长时间压测，但已经出现的幂等、调度和数据隔离问题会直接影响约定，必须跟进。增加相关用例是对证据缺口的补充，不需要因此再建测试平台或重做系统架构。

## 协作体会

这轮协作中，AI 把分散讨论转化为方案、代码和检查，开发者则通过具体反馈持续调整方向：固定约束，收窄成功判定，补清错误处理，限制组件和验收规模，并在实现报告完成后继续要求复核。人的参与贯穿需求、取舍和交付判断，不能只体现在最初的一段提示词里。

使用 AI 时，容易低估的是检查前提所需要的工作。一段方案即使解释得很顺，也可能依赖尚未确认的需求，或者把未来可能用到的能力放进第一版。持续追问适用条件、保留必要取舍，并把不确定的结论交给验证，才能让讨论真正帮助项目向前推进。

最终取舍和交付判断仍由开发者负责。协作说明同时保留已经修正的问题、后续复核发现的缺陷和未验证范围；只有相应改动与检查真正完成后，才能更新解决状态。代码生成速度、提交数量和一次测试通过，都只能作为过程信息，不能代替这项判断。
