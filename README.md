# rc_celanwang - API 通知系统设计

## 问题理解

企业业务系统在注册、付款或交易完成后，需要向广告、CRM、库存等供应商发送 HTTP(S) 请求。供应商的地址与请求格式不同，响应速度和可用性也不受业务方控制。让每个业务系统独立处理重试和恢复，会重复建设相同机制，并让外部故障影响主业务流程。

本方案由业务方确定通知时机、目标和请求内容，通知服务在持久化后接管投递。一条通知对应一个目标请求，多个目标独立处理。服务需要使每条已接收通知有可查询的状态，在进程异常后恢复处理，并让长期失败能够被发现和处理。

第一版收到供应商返回的有效 `2xx` 状态码（200 至 299）后，将通知标记为投递成功并停止重试。服务不检查响应正文中的业务处理结果，也不继续查询供应商是否完成后续操作。因此，“投递成功”不等于“供应商业务处理成功”。

服务的责任从持久化接收开始。业务事务成功但尚未提交通知的缺口，需要业务侧通过事务内保存待发事件等方式补足。库存场景按交易后的结果同步理解，交易时的库存预占、严格顺序和跨系统事务不属于这套异步投递机制的保证范围。

## 架构设计

系统采用一个 Go 服务，在进程内划分接入、调度、投递和策略模块。MySQL 保存任务与尝试记录，后台 Worker 从数据库领取到期任务；外部 HTTP 请求的执行和结果分类在领取事务提交后进行。

接入过程完成鉴权、请求校验和幂等检查，数据库提交成功后才返回任务 ID。调用方以同一个幂等键重试提交时，内容相同则返回已有任务，内容不同则返回冲突。调用方连接结束后，已持久化任务仍由后台独立处理。

任务使用 `pending`、`processing`、`succeeded`、`failed` 四个状态，分别表示等待、处理中、投递确认成功和本轮自动处理停止。`notification` 保存当前状态与调度信息，`notification_attempt` 保存每次执行的响应、错误和耗时。失败原因与状态分开，便于区分一次暂时错误和整轮停止。

Worker 领取时写入租约和领取令牌。租约规定任务何时可以被回收，令牌用于验证谁有权写回结果。执行中断后，回收流程重新判断任务是否继续；旧执行者不能覆盖已被接管的任务。任务与尝试结果在同一事务中更新，外呼期间不持有数据库事务。

HTTP 与 HTTPS 共用投递逻辑。连接、响应和资源均有上限，HTTPS 校验证书和域名，目标访问受权限限制，重定向不自动跟随。暂时故障按退避策略重试，次数或有效期耗尽后保留停止原因和历史，修复后可以受控重放。按目标限制并发和公平分配执行机会，使一个慢供应商不占满所有 Worker。

## 决策取舍

MySQL 同时承担任务保存和调度状态管理，使接收、去重与状态变更可以使用同一套事务，减少数据库和消息队列双写问题。代价是轮询、状态更新和历史记录消耗数据库资源，需要索引、归档和压测。只有在这些优化后仍出现调度瓶颈，才增加独立消息队列。

投递采用允许重复的至少一次思路。供应商可能已经执行，但响应丢失或成功结果尚未写回，重试有利于避免漏送，也可能重复产生副作用。接收幂等不能替代供应商幂等；业务方需要接受重复请求，或使用供应商支持的稳定业务标识。服务不承诺业务效果恰好一次。

自动重试同时限制次数和有效期，避免长期故障产生无界请求与积压。停止后保留查询、原因和重放入口，意味着恢复依赖故障被发现与修复；供应商永久不可用时不能保证最终取得成功响应。生产持久性还依赖数据库配置、存储及备份恢复能力。

四态状态机、两张核心表和显式 SQL 足以表达当前生命周期。单服务内按职责划分模块，可以减少部署和协调成本，但需要明确的资源隔离。通用工作流、动态签名平台和微服务拆分暂不进入第一版；后续分别根据真实的流程差异、供应商协议和独立扩缩容需求扩展。
